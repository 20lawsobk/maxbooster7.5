# Current SQL and PDIM joint recovery rehearsal

Run `node --import tsx --test tests/current-storage-joint-recovery.test.mjs` from the repository root. The master test runner also discovers this suite. Use the supported Node runtime, installed repository dependencies and a matching PostgreSQL client/server toolchain: `initdb`, `pg_ctl`, `pg_dump` and `psql` must be on PATH. No application, provider or production database credentials are needed. Linux needs the PostgreSQL shared libraries available to these tools.

The test starts its own Unix-socket-only PostgreSQL cluster and two successive, independent canonical local PDIM owner processes on ephemeral loopback ports. It uses production storage repositories, immutable byte containers, the fsynced canonical PDIM AOF, the authoritative pinned-descriptor snapshot export, PostgreSQL tool selection, `pg_dump` and transactional `psql` restore. The helper is [helpers-current-storage-joint-worker.ts](../../tests/contracts/helpers-current-storage-joint-worker.ts); it is a fixture process, not a standalone test or production recovery command.

Five acceptance steps execute:

1. Write synthetic private/public files through the current hybrid service. Verify cross-owner deduplication, retain an interrupted upload and deletion, create completed/expired media jobs, reserve a current fabric migration and delete an immutable replica to create its permanent tombstone. Await every fixture writer, then export the actual canonical checkpoint through its pinned file descriptor. No legacy ownership index is written or substituted.
2. After the source application process exits, keep a read-only exported PostgreSQL snapshot open while the production dump helper runs real `pg_dump`. Retain the original plain SQL dump and current PDIM JSON checkpoint, both with mode `0600`, inside an independent private recovery directory.
3. Bind these retained artifacts with a recovery UUID, byte counts, SHA-256 digests, the existing PDIM manifest and matching synthetic SQL/PDIM markers. Reject corrupted SQL, corrupted PDIM, an unrelated pair UUID and a crossed PDIM manifest before starting `psql` or changing protected SQL/file sentinel targets. This pair manifest is rehearsal bookkeeping, not a new archive format or production restore API.
4. Drop the original source database and remove its process directory. The restored service cannot consult either source location.
5. Admit the verified retained pair, restore into a fresh SQL database in a single transaction with a schema-qualified pair invariant, and start a fresh canonical PDIM owner from the retained checkpoint. Assert exact file hashes, owner denials, public reads, dedup survival after primary deletion, no deleted-file resurrection, owned pending-upload/deletion recovery, media-job owner/expiry handling, migration completion/accounting and retained tombstone rejection of a stale write.

The private dump, checkpoint, fake ownership records and temporary databases are deleted during cleanup. Reports under [reports/recovery-acceptance/2026-10-27-current-sql-pdim](../../reports/recovery-acceptance/2026-10-27-current-sql-pdim/) contain counts, digests, runtime/source identities and assertions; they contain no database dump or PDIM payload. Each invocation retains a separate receipt. Failed attempts remain labelled `failed`; only a completed independent restore writes a passing receipt.

This closes the controlled current-format storage recovery rehearsal gap. Earlier legacy-format drills remain historical and correctly retain `currentSqlMetadataRecovered: false`. This suite uses a minimal schema for the relevant current storage, media and migration tables; it does not certify recovery of every application table. The source writers are deliberately drained. It does not establish consistency while independent production writers remain active, an automated production joint-backup orchestrator, retained offsite copies, deployed Neon/Replit recovery, live migrations, measured RPO/RTO or global capacity. Those operational gates require their own evidence.
