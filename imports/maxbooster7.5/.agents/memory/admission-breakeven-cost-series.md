---
name: Cache-admission breakeven cost-series separation
description: When gating cache/pocket admission on a measured cost-vs-benefit breakeven ratio, keep every-call, hit-only, and miss-only costs as separate EWMA series instead of blending them.
---

An admission gate that decides "is caching worth it here" from measured timings is comparing costs paid by DIFFERENT call types: some cost (e.g. hash + lookup) is paid on every call, some cost (e.g. copying a stored result back out) is paid ONLY on a hit, and some cost (e.g. computing + storing) is paid ONLY on a miss. Folding a hit-only cost into the "paid every call" series (e.g. adding copy time into an `overhead` accumulator that also updates on misses) still produces a plausible-looking number that doesn't crash — but it silently drifts the derived ratio away from the formula the code claims to implement. The bias direction depends on hit rate, so a fixed-value unit test can pass right through it; only re-deriving the algebra by hand and comparing exposes the mismatch.

**Why:** Found in MaxCore's PocketAccelerator adaptive-gating admission logic (`external/maxcore/artifacts/ai-training-server/ai_model/maxcore/pdim/pocket_accelerator.py`): the first implementation added a hit-only `copy_seconds` into the same `overhead_ewma` series that hash+lookup (paid every call, hit or miss) updates. It wasn't a crash or an obviously-wrong number — the existing `max(static_floor, breakeven)` guard and a zero/negative-denominator guard already prevented worse-than-baseline outcomes — but the resulting ratio didn't match the "expected cost per call WITH caching vs. WITHOUT it" derivation the docstring described. Corrected formula: `breakeven_hit_rate = (overhead + store) / (compute + store - copy)`, with `overhead` (hash+lookup, every call), `copy` (hit-only), and `compute`/`store` (miss-only) each tracked as their own EWMA.

**How to apply:** Before implementing any cost-ratio/breakeven gate, write out the two scenarios being compared algebraically first (cost per call with the optimization vs. without), identify which term is paid by which call type (always / hit-only / miss-only), and give each its own accumulator — only combine series when the combination is what the formula's numerator/denominator actually calls for. Guard the denominator against zero/negative (e.g. a hit-only cost that happens to exceed what it replaces) by skipping the posterior adjustment for that call rather than dividing by a non-positive number. Grep for every existing consumer of a pre-refactor combined field before splitting it — downstream stats/telemetry code may read the old aggregate name and should keep working unchanged if it was already correct at that level.
