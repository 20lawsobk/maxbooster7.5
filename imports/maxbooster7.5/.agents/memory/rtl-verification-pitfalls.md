name: RTL/testbench pitfalls found while pushing a GPU core through real synthesis
description: General (not sky130-specific) Verilog RTL and testbench lessons -- synthesis dead-code elimination via missing observable I/O, a reserved-keyword parse cascade, and a blocking/NBA same-edge race that corrupted every other word of a loaded program.
---

## A module with no real dependency from its only primary output gets synthesized down to ~nothing
A SIMT core whose only top-level output was `halted` synthesized to 2 cells (a clock inverter and one flip-flop) even though the RTL had a full register file, ALU, and memory. The synthesis tool was correct: nothing in the design's actual primary-port fanout depended on the register file or memory contents — the original testbench only ever observed them via simulator-only hierarchical pokes (`dut.regfile[...]`, `dut.gmem[...]`), which are invisible to a synthesis tool's dead-logic elimination.
**Why:** synthesis (and `check`/`stat`) only preserve logic that's reachable from a real primary output or a state element with an externally observable effect. Hierarchical testbench access proves a simulation matches intent; it proves nothing about synthesizability.
**How to apply:** before trusting any synthesis cell count/area as "real," confirm the design has actual primary-port read/write paths reaching every functional unit you care about (add a load port and readback port if it doesn't). Treat a suspiciously tiny post-synth cell count on a nontrivial design as a real finding to investigate, not a tool bug.

## A reserved SystemVerilog keyword as an identifier produces a cascading wall of unrelated errors
Naming a `reg` array `program` (valid in plain Verilog-2001, but a reserved keyword in SystemVerilog for `program ... endprogram` blocks) compiled fine under a Verilog-only toolchain but broke immediately under `iverilog -g2012` (SystemVerilog mode) — the parser choked at the declaration and then threw dozens of unrelated-looking "syntax error" / "Syntax in assignment statement l-value" errors on every later line that referenced the array, none of which mention the real cause.
**Why:** a parser desync from one bad token corrupts its state for everything downstream in the same file; the first reported line is the real cause, later ones are usually noise.
**How to apply:** when a `-g2012`/SystemVerilog-mode compile produces a large cluster of unrelated-looking errors, fix only the *first* reported line/error and recompile before reading any of the rest — don't try to interpret the downstream noise.

## Driving a synchronous DUT input with blocking assignments in a `for` loop can race the DUT's own always block on the same edge
A testbench loop of the form `for (...) begin we=1; addr=k; data=D(k); @(posedge clk); end` looks race-free (values are stable for a full period before the edge) but isn't: once `@(posedge clk)` resumes, the loop's *next* iteration immediately re-assigns `we`/`addr`/`data` with blocking assignments in the same Active region where the DUT's `always @(posedge clk) if (we) mem[addr] <= data;` is also scheduled to evaluate for the edge that just occurred. Verilog does not define the relative order of two different processes woken by the same event, so depending on simulator scheduling, the DUT's write can sample the *next* iteration's values instead of the current edge's — here it deterministically corrupted every other word of a loaded program (write for word `k` silently used word `k+1`'s address/data instead).
**Why:** this is the classic "testbench races the DUT for the same clock edge" hazard; it reproduced in a from-scratch 15-line isolated memory-write test, confirming it's a fundamental Verilog scheduling hazard, not specific to any one design.
**How to apply:** when a synchronous write-port testbench loop shows a suspicious alternating/every-other-word corruption pattern (or any pattern that flips if you re-order the loop slightly), suspect this race first. Fix by resuming strictly after the edge's NBA region settles before driving new stimulus: `@(posedge clk); #1; <drive next values>;` (equivalently, driving on `@(negedge clk)` while the DUT samples `@(posedge clk)` also works). Verify the fix on a minimal standalone reproduction before trusting it on the real design.
