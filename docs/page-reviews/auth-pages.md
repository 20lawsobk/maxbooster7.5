# Authentication page review

## Scope and preserved policy

Initial owned changes covered Login, Register, ForgotPassword, ResetPassword and focused unit checks. Ownership subsequently expanded for the confirmed age policy to registration/checkout/Google signup portions of `server/routes.ts`, signup schemas, consent/support age claims, RegisterPayment, Terms and a shared age helper. No live sign-in, demo, registration, reset, email, payment or database operations were performed. AuthProvider/account-coordinator integration was preserved, not reimplemented.

The user explicitly resolved the minimum account age to **16** (`.agents/memory/minimum-account-age.md`). Eligibility now applies to new account creation; existing accounts are not deleted, disabled, modified or backfilled by this change. Canonical $49/$468/$699 pricing was not changed. Existing 90-day guarantee copy was preserved.

## Confirmed age-16 implementation

- `shared/agePolicy.ts` is the common policy for normal signup, checkout, paid completion, schemas, consent age validation and the registration UI. It requires a real, exact `YYYY-MM-DD` calendar date, rejects normalization (for example February 30), future/missing dates, and calculates the sixteenth birthday using UTC calendar fields. February 29 birthdays advance on March 1 in non-leap years.
- Register now collects a required birthday without defaults. Email signup sends it in the JSON body; the server validates it before any account creation. RegisterPayment uses the same validator and age-16 explanation before contacting checkout. Public checkout validates before creating a Stripe session, and paid completion independently revalidates the DOB in Stripe's retrieved metadata before creating a new user. Old paid checkouts missing valid eligibility fail explicitly with a contact-support-before-repurchase instruction; no fictitious DOB is supplied.
- New Google signup first submits DOB in the body of `POST /api/auth/google/signup`. This rate-limited endpoint explicitly requires CSRF despite the existing OAuth exemption. After validating age it stores only a ten-minute server-owned receipt (`minimumAge`, expiry), **not DOB**, in the session. GET initiation binds that receipt to its random OAuth state and explicitly saves state before redirecting. The callback consumes state/receipt and permits a new account only with a current age-16 receipt bound to that state. Expired/wrong-state/old-policy/missing receipts cannot create accounts. A rejected replacement eligibility request clears the previous receipt.
- DOB is absent from OAuth URLs, Google requests, redirect errors and OAuth session receipts. A login initiated without DOB remains supported for **existing** Google/password accounts. A verified Google identity that would be a new user is redirected to Register to collect eligibility, then can retry the supported Google flow. Missing DOB is never treated as eligible and Google signup was not disabled.
- Terms now state age 16 for new email, Google and paid registration. Privacy already stated 16 and was not changed. The consent service and the support answer no longer claim 13 or an under-13 parental-consent exception. No broad legal-compliance certification is asserted by this engineering review.

### Alternate creation-path assessment / scope boundary

The focused account-write search found all four `storage.createUser` call sites in live `server/routes.ts`: ordinary signup, Google callback, paid signup, and the system demo-account bootstrap. The three human public-registration paths are gated; password/Google existing-account login is not gated. Demo is a platform-owned synthetic showcase account, not new human enrollment; no fake DOB or age backfill was added.

Other direct user inserts found: `server/init-admin.ts` and `server/scripts/setupAdmin.ts` are operator bootstrap scripts; they were left unchanged. `server/services/ssoService.ts` has SAML and OIDC just-in-time provisioning and SCIM creation methods with direct `db.insert(users)` calls. The targeted call-site search found **no callers** of `handleSAMLResponse`, `handleOIDCCallback` or `createSCIMUser`; current workspace routes configure/test SSO but do not invoke those provisioning methods. These dormant service methods are **not age-gated** and are outside the explicitly granted service ownership. Coordinator follow-up/ownership expansion is required before exposing or relying on them for signup: define trusted eligibility claims or an interactive age-16 enrollment step and enforce the shared validator before new-user inserts, without restricting existing users. This review does not claim every dormant/operator creation primitive is covered.

## Read-only contract trace

- `server/routes.ts`, POST `/api/auth/login`: accepts `username` or `email`, password, optional `twoFactorCode`. MFA challenge is HTTP 200 with `requiresTwoFactor: true`, **not** an authenticated user. Success is a top-level safe user with string `id` and nullable bearer `sessionToken`; invalid/replayed TOTP is 401. Cookie session is authoritative when no token is returned.
- POST `/api/auth/demo`: top-level safe user plus `isDemo: true`; no bearer is issued. This endpoint can create/update the demo account, so it was **not called**.
- POST `/api/auth/register`: accepts username/email/password/confirmation and optional artist name; establishes a cookie session and returns a top-level safe user. Duplicate messages are `Email already registered` and `Username already taken`. Username regex allows 3–30 letters/digits/underscores. Minimum password length is eight; artist discovery is asynchronous, not guaranteed on response.
- POST `/api/auth/forgot-password`: trims email; HTTP 200 `{success: true}` deliberately does not establish account existence. Reset links expire after one hour. Provider rejection is 503; a false delivery-success screen must not be shown.
- POST `/api/auth/reset-password`: consumes `{token, password}`, checks 8–72 character length, atomically consumes the hashed single-use token and advances the account session epoch, returns `{success: true}`. Invalid/expired/already-consumed tokens intentionally share an ambiguous error.
- `server/middleware/csrf.ts`: login/demo require cookie/header CSRF; register/forgot/reset are currently exempt. Login/demo bootstrap `/api/csrf-token` if needed. No automatic replay of credential/reset POSTs was added.
- Google callback emits `unverified_identity`, `identity_mismatch`, `account_unavailable`, and `authenticator_recovery_required` in addition to existing errors. MFA-enabled Google accounts are redirected to the backend challenge, not the password MFA form.

## Page fixes

- All four pages have immediate ref-based duplicate-request guards, disabled relevant controls, guaranteed `finally` recovery, and 30-second per-fetch abort deadlines.
- Login validates MFA before sending, keeps replay/fresh-code guidance, does not confuse a CSRF error with invalid credentials, and checks response identity. Password/MFA and demo requests now run through the coordinator-provided `AuthProvider.authenticate` boundary; the provider exclusively owns token handling, authoritative session verification and cache completion. Safe internal redirects reject protocol-relative/backslash/control-character targets. A page-local authenticated redirect respects that validated destination rather than racing the shared hook's unconditional dashboard redirect.
- OAuth error cleanup preserves unrelated query/hash parameters. Newly traced Google errors and unknown OAuth failures have explicit safe messages.
- Registration now waits for the initial auth check, handles non-JSON/malformed responses explicitly, refuses success without a valid user ID, and only labels actual duplicate-account messages as duplicates. Its request/parsing also runs inside `authenticate`; no page-local bearer or auth-cache mutation remains. Provider verification failures stay explicit rather than being mislabeled as connectivity failures. Password visibility controls have labels, the 30-character username boundary copy is accurate, and Google signup cannot bypass this page's terms checkbox. This is a client gate, **not** evidence of durable consent recording.
- Forgot-password transport requires boolean `success: true` on both initial and resend requests. Both paths retain explicit errors, use conditional/account-neutral success copy, and prevent recipient switching during an active resend. Existing cooldown/timer cleanup is retained.
- Reset shows the missing-token screen immediately, enforces the backend's current length bounds, sends only the consumed fields, requires boolean success, preserves invalid-or-expired ambiguity, surfaces throttling, provides a new-link action, clears password state on success, and associates field errors with their inputs.

Browser/E2E verification is explicitly deferred under the memory-safety instructions.

## Exact shared follow-ups / remaining blockers

1. **Account-transition integration — page wiring completed:** the coordinator added `authenticate<T extends AuthenticationExchange>(request): Promise<T>`. Login password/MFA, demo and registration now supply their fetch-and-parse callbacks to it, including login/demo CSRF bootstrap and existing deadlines. Existing response error/MFA branches and redirect behavior remain after the returned exchange. Both page gates read `user`/`isLoading` directly from provider `useAuth`, hide their forms for an already-authenticated provider user, and contain no independent auth observer or `/api/auth/me` fetch. Direct page `setAuthToken`, `setQueryData` and query-client imports are removed. The boundary owns cleanup/exclusive lease, cookie-only token clearing, shared-lease `/api/auth/me` verification, identity matching and provider unlock; failed/challenge exchanges do not unlock. Provider-boundary behavior and cross-tab isolation tests remain coordinator-owned.
2. **Revocation visibility:** reset advances session epoch, but `AuthProvider` auth queries have infinite staleness and no focus/reconnect refetch. Coordinate successful reset and server 401 handling with authoritative session revalidation/clearing so a revoked cached user is not treated indefinitely as signed in. Include cookie/JWT/cross-tab tests; do not assume local reset page success verifies this.
3. **Age resolved; durable consent remains separate:** age 16 is now centrally enforced for live human signup paths, including Google. The existing terms checkbox is still not a complete versioned, durable consent record for ordinary/OAuth signup. Define that contract independently; this change does not invent DOB persistence columns, migrations, fake dates, historical age flags or retroactive account restrictions. Dormant SSO provisioning is the explicit boundary noted above.
4. **Backend password contract consistency:** registration currently lacks reset's upper bound; both hash with bcrypt. Coordinate a shared password validator and explicit UTF-8 byte versus character policy (bcrypt's truncation boundary), then align both pages. This review only matches reset's existing character-count contract; it does not introduce a new password policy.
5. **Ambiguous registration failures:** an account may be persisted before session save fails. Backend currently returns generic 500 in that case. Define an explicit account-created/session-failed outcome or safe sign-in recovery so users are not encouraged to repeat account creation after an ambiguous timeout/session failure.
6. **Forgot-password enumeration caveat:** known-account provider failure returns 503 while unknown-account requests return success. The page no longer claims existence/delivery, but provider-outage response asymmetry remains a server-side privacy decision. Keep genuine send failures explicit while designing a non-enumerating asynchronous delivery/status contract.
