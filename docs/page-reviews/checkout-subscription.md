## Implemented frontend changes

- Both purchase summaries now lead with canonical **Monthly $49/month, Yearly $468/year, Lifetime $699 once**. Annual copy identifies $39/month as an equivalent, $468 annual billing, and $120 savings. Subscribe now includes the required **90-day money-back guarantee**. Removed unused fabricated Stripe price-ID strings.
- Both tier lookups reject inherited object properties such as `constructor` and `__proto__`.
- RegisterPayment validates the backend's username shape, email format, actual calendar birthdate (including overflow/future dates), and minimum age before creating checkout. Trims identifier/email/artist input and limits artist-name length. Retains the existing server minimum age of 13 rather than silently changing policy.
- RegisterPayment uses a synchronous ref lock against repeated submit events, renders inline errors, and validates returned checkout URLs as HTTPS on `checkout.stripe.com` without URL credentials before navigating. Backend/provider-domain changes require a deliberate update, not an unrestricted redirect fallback.
- RegisterSuccess requires explicit `{ verified: true }`, not merely HTTP success, before displaying the account form/payment-success heading. Auth-loading is respected. Reuses the in-flight verification promise across effect repeats; failure offers manual verification retry, sign-in, and support guidance without encouraging another purchase.
- RegisterSuccess aligns password validation and input minimums with the backend's eight-character minimum, validates consent as literal true, guards submission on verified state, and locks duplicate account submissions. Adds inline account errors, password-toggle accessible names, and safe external policy-link attributes. Removes the pre-registration claim that subscription access is already active.
- RegisterSuccess now routes its **actual session-establishing registration exchange** through `AuthProvider.authenticate`. The legacy endpoint returns `{ user: { id, ... }, message }`; the page explicitly validates `user.id` and adapts it to the boundary's top-level `data.id`. It does not pass checkout/session-verification responses to authentication, mutate shared token/cache/identity state, or force a reload. Dashboard navigation and welcome occur only after the provider resolves its independent verification.
- Subscribe waits for auth loading and preserves the intended login redirect. It does not create provider objects when the public Stripe configuration is missing.
- Subscribe memoizes setup requests and idempotency keys by authenticated user ID and tier, retains the key on request failure, ignores stale route/account responses, clears old session display, validates client secrets, and remounts Elements for the current session.
- Card-confirmation retries stay on the existing intent instead of calling subscription creation again. Confirmation has a synchronous duplicate lock; payment-form readiness/load errors and unexpected payment statuses are surfaced. Redirect-required returns no longer label the dashboard URL as payment success merely because Stripe redirected. A succeeded SDK payment reports server-confirmation timing rather than claiming entitlement activation.
- Added actionable policy links and removed unsupported estimates about payment-service recovery time.

## Read-only backend / shared contract trace

- `server/routes.ts`, public registration checkout: validates tier/email/username/birthdate, checks duplicate identities, uses server-selected price IDs, returns `{ url, sessionId }`. Checkout success goes to `/register/success?session_id=...`, cancellation returns to the same payment tier. Registration-checkout idempotency is server-generated from identifiers/tier and a short time bucket, not a client-controlled durable intent.
- `/api/verify-checkout-session`: server retrieves Stripe session, requires paid status, expected mode, and matching configured line-item price; returns only `{ verified: true }`. It is not an authentication endpoint.
- `/api/register-after-payment`: repeats paid/plan verification, rejects existing accounts instead of logging them in, requires eight-character password and policy acceptance, creates account, updates subscription fields, regenerates/saves an actual login session, returns nested `user`. Session-save failure explicitly tells the client to sign in.
- `/api/create-subscription`: authenticated, accepts `planName`, requires a valid `Idempotency-Key`, returns a payment-intent/subscription client secret via `server/services/subscriptionCheckoutService.ts`. Service validates USD amount/type/cadence against 4900/46800/69900 cents, records provider references and replays saved operation results. It is not an auth exchange.
- `client/src/lib/authenticationBoundary.ts` / AuthProvider: successful actual authentication must supply a nonempty string `data.id`; provider owns account cleanup/token handling and independent `/api/auth/me` verification. Nested registration identity adaptation is local to the actual registration exchange.
- `client/src/lib/queryClient.ts`: ApiError maps status and user-facing errors but does not retain arbitrary backend `code`/`retryable` fields for all statuses.
- `server/routes/webhooks/stripe.ts`: checkout/subscription and payment-intent handlers are separate from UI confirmation, with subscription-tier/period updates and lifetime fulfillment. Provider event delivery and entitlement convergence were not exercised.

## Coordinator-owned boundaries and remaining risks

1. **Shared API-error metadata is lossy.** Backend reconciliation/idempotency/schema errors include actionable codes and `retryable:false`; ApiError can replace these with generic HTTP-derived codes/retryability. Subscribe no longer assumes nonexistent `error.body`, but cannot reliably distinguish these cases without a shared error-contract change. Preserve approved backend billing codes/retryability in the shared wrapper and test them; do not invent provider endpoints or change shared error code unions blindly.
2. **Auth response shape is legacy.** The page adapts a validated identity from the actual session-establishing endpoint; checkout receipts are never authenticated. A coordinated backend change to emit the standard top-level auth response would remove this adapter. Shared-boundary/account cleanup, mismatch behavior, and registration's cookie session require serialized integration verification. If the session is created but client verification fails, normal sign-in/support recovery is required rather than another purchase.
3. **Post-payment registration persistence needs backend review.** The inspected path writes tier/estimated end dates but does not visibly persist checkout customer/subscription IDs in that update. It uses 30/365-day estimates and a 2099 lifetime date, rather than a demonstrated canonical provider billing period. Birthdate/consent/marketing persistence is not established by this endpoint. The page sends marketing consent, but the inspected endpoint does not consume it. Do not claim these records or recurring renewal/cancellation synchronization are proven.
4. **New-user checkout idempotency is not durable across arbitrary retries.** Frontend guards stop concurrent same-mount submissions; server time-bucket keys do not establish safe lost-response or cross-tab replay. Subscribe keys are scoped to the mounted page/user/tier, not durable across reloads/tabs. Durable checkout-intent recovery and prevention of duplicate subscriptions across independent visits need backend/product ownership.
5. **Age-policy conflict remains:** enrollment backend/UI minimum is 13 while the previously reviewed Privacy page says under-16 users are not intended. Legal/product must decide before changing policy or enrollment ages.
6. **Feature/entitlement marketing drift remains** across these pages and Pricing/billing plans. Approved storage/support/feature limits were not evidenced, so existing feature arrays were not invented or reconciled.
7. **Provider/entitlement evidence missing:** actual configured prices, Stripe SDK readiness, redirects/SCA, payment decline/retry, webhook replay, activation timing, subscription lifecycle, refunds/90-day guarantee fulfillment, expired sessions and account/session failures require authorized serialized testing. No UI query parameter is treated as entitlement proof.
8. **Browser evidence absent.** Layout, mobile, keyboard/focus, real provider Elements errors, authenticated screens, route transitions and full account isolation were not visually or end-to-end verified. The coordinator must finish the corrected isolated suite before relying on it, then separately validate allowed browser flows without real transactions.

The isolated suite is intended to cover invalid tiers, canonical price/guarantee copy, input/calendar/age validation, duplicate submission/normalization, untrusted checkout redirects, explicit verification/retry, password length, actual-auth adaptation/failure, auth/config guards, setup-key reuse/missing secret, stale tier responses, and duplicate/unexpected payment confirmation. It imports no backend modules and uses only stubbed HTTP/Stripe boundaries.
