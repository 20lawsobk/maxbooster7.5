## Follow-up source completion (supersedes AG-1/AG-2/AG-4 partial source findings above)

### AG-4 — addressed expected-review revision protection

`kycReviewRevision.ts` builds a canonical SHA-256 digest over identity/verification state and the complete, ID-sorted document evidence records (IDs, object references, status, reviewer metadata and validity dates). Admin list responses include `reviewRevision` on each verification and document. Both review API handlers require a valid `expectedRevision` and all three service commands (approve verification, reject verification, review document) recompute it after acquiring the parent verification row lock. A stale reviewer gets **409 without a mutation**. The actual KYCReview page now submits the revision from the displayed record for approve/reject/document decisions. Successful approval persists the immutable canonical reviewed snapshot and digest in existing JSON metadata; document decisions record their reviewed digest. Upload and identity-edit paths share the parent-row serialization contract already implemented.

No schema migration or hypothetical consumer. Digest is of evidence records/references, **not a claim to have hashed bytes in remote storage**. Immutable object custody and historical verified-row revalidation remain operational/data gates. UI stale-selection behavior is explicit reload-required conflict rather than silently applying a decision to new evidence.

### AG-1 — addressed scoped idempotent decision commands

All primary review/remove/warn/ban handlers and the later admin router's generic moderation action now call the same transaction service. Commands require `Idempotency-Key` header or body `idempotencyKey` (16–128 alphanumeric/dash/underscore characters). The Admin page generates one key per opened decision and retains it on retries. The service takes a transaction-scoped PostgreSQL advisory lock on actor+key, then reads durable audit receipts scoped to that actor/key. Same intent replays its original timestamp/result without another notification/mutation; changed intent with a reused key returns 409. Audit receipt (intent fingerprint, result and key), content/user effect and in-app recipient notification commit atomically. Actor scope prevents another admin's key from replaying someone else's decision. Missing targets return 404; self-ban is rejected. Warning severity is included in the fingerprint and durable notification/audit metadata.

This uses existing `audit_logs`, not a new case table. **Retain moderation command receipts for the supported retry horizon; deleting them forfeits deduplication after that retention boundary.** Full reporting intake/provenance remains distinct from this effective flagged-post decision queue. No remote deletion or timed suspension is claimed; the pre-existing direct ban route no longer echoes arbitrary durations it does not enforce.

### Exact exported control signatures

From `server/services/governancePolicyService.ts`:

- `readGovernancePolicy(): Promise<{ maintenanceMode: boolean; userRegistrationEnabled: boolean; apiRateLimit: number }>` — uncached DB read; throws `GovernancePolicyUnavailableError` with `statusCode = 503` for storage or validation failure.
- `enforceMaintenance: RequestHandler` — uses resolved `req.user.role` for authenticated admin exemption; 503 plus Retry-After for maintenance; requires main's explicit recovery/webhook exclusions before mounting.
- `assertRegistrationEnabled(): Promise<void>` — throws `RegistrationDisabledError` with `statusCode = 403` if disabled; propagates unavailable-policy 503.
- Both error classes are exported. Main can map `statusCode` without string matching or treating a DB outage as registration-open.

Existing `globalScalableRateLimiter` and `apiRateLimiter` exported RequestHandlers are already the runtime-governance consumers; main need not add another limiter or change their call signatures.
