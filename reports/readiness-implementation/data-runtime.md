## Scope and release decision

Implemented the recommended strengthening direction, not the alternative architectures. **Not a production-readiness sign-off.** Application remained stopped. No workflow, provider, database, secret-value, dependency-install, payment, message-send, or model-training operation was performed. Tests use temporary files and mocked DB/provider/process boundaries; no full typecheck or suite was run.

Several acceptance gates require information or operations expressly prohibited in this task: existing backup/PDIM inventory, live-state export, reviewed migration application, isolated real PostgreSQL/Redis crash tests, and a recovery/promotion drill. These are blockers, not successful verifications. Do not deploy the external PDIM recovery format change over legacy state without the migration described below.

## Required shared-file integration patches (not applied by this owner)

### server/index.ts — backup lifecycle

After DB/migration readiness and before the current retention startup block (the block importing `getRetentionQueue, startRetentionWorker`), add:

```ts
const { databaseBackupService } = await import("./services/backup/databaseBackupService.js");
await databaseBackupService.initialize();
```

In `gracefulShutdown`, before database connections are closed, add:

```ts
const { databaseBackupService } = await import("./services/backup/databaseBackupService.js");
await databaseBackupService.stop();
```

`initialize()` remains disabled outside production/deployment unless `ENABLE_BACKUPS=true`. Failed catalog/lease operations are surfaced and visible in metrics/logs, not treated as verified backup success. Parent owns readiness policy; do not report scheduled backups operational until migrations + initialization + actual schedule verification pass.

### Shutdown follow-up — active scheduler drain implemented

`DatabaseBackupService.stop()` now returns a shared drain promise (default **20 seconds**, optional shorter deadline for isolated tests). It synchronously fences cron/catch-up dispatch, stops cron, and waits for all already-dispatched run promises, including claim, dump/upload, retention, terminal run-state write and in-flight heartbeat renewal queries. Runs are registered before their first async work; repeated stop calls observe the same result. A stopped instance cannot be reinitialized.

Heartbeat ownership belongs to the tracked run, not the cron timer: normal shutdown does not clear a live run's heartbeat. The terminal/failure path clears the interval only when work no longer needs ownership and then drains already-issued renewal queries before releasing the tracked run. A failed upload preserves its pending catalog record and records a failed run if the durable authority is available.

If the drain deadline expires, stop **rejects explicitly** rather than falsely reporting completion, marking live work failed or abandoning ownership. The live run remains tracked and keeps renewing until its actual terminal path, or process termination. If the process terminates first (the parent currently has a 25-second hard shutdown deadline), the uncompleted SQL lease is retained and becomes recoverable on expiry. No new run dispatch is allowed after timeout. This intentionally does not pretend that an uncancellable provider operation was cancelled.

The operator restore CLI now also awaits stop before closing the pool. No shared boot/shutdown file was edited in this follow-up.

### Security coordination — do not silently assume sibling integration

Follow-up authorization assigned the existing `sessionConfig.ts` revocation wrapper to this domain. It now awaits `services/sessionAuthority.ts` durable `revoke` and returns `{confirmed:true}` only after the statement resolves; failures propagate. This is durable-statement confirmation, not a claim that a separate readback was performed. Security callers may ignore the resolved result.

The selected PG store directly calls `sessionAuthority().validate(userId, session.authGeneration)` on every authenticated read. The previous deployment gap (bypassing revocation until middleware was mounted) is closed at the store boundary. Security still owns epoch issuance/stamping, epoch SQL migration, account-state transitions, MFA, and route integration. Its additional `validateSessionAuthority` middleware may remain a defense in depth after express-session; the store does not assume it is mounted. Existing sessions without a generation do not receive a permissive migration fallback.

No `server/routes.ts`, `server/index.ts`, `server/storage.ts`, `shared/schema.ts` or client shared files were edited here.

## Legacy PDIM conversion and safe cutover runbook

New tool: `scripts/convert-pdim-legacy-recovery.mjs`. It uses only local filesystem and Node crypto; it does not import application modules or contact a DB/provider. It never mutates input files or overwrites an existing output directory. Originals and operator approval are copied byte-for-byte into a new mode-0700 directory; files use mode 0600. `READY.json` is written last and contains hashes plus a manifest-last upload plan. The converted artifacts are consumed by the real RedisStore recovery loader (exercised in the fixture test).

1. **Do not deploy/restart legacy PDIM with new recovery code yet.** Obtain a separate authorized maintenance window and verified retained copies of its object metadata/storage. Fence ALL writers/replicas but keep the old in-memory store available until live stream export is complete. Application-stopped status does not prove the external service is fenced.
2. Under that fence, obtain a completed final legacy snapshot and its AOF from the same instance, and a complete live stream export including entries, group last-delivered IDs, pending deliveries/counts and consumer timestamps. Use a separately authorized export mechanism with access to actual in-memory state. This task did not add an unauthenticated export endpoint or execute an export. Never invent an empty stream export when completeness is unknown.
3. Require snapshot `version:1`, integer `baselineSeq`, integer millisecond `savedAt`, and `entries` in existing RedisEntry format. AOF must be `{version:1, records:[{s,c,a},...]}`; all records must already be folded (`s <= baselineSeq`) with contiguous retained sequence numbers. If any uncheckpointed tail exists, finish a clean checkpoint on the fenced old owner and re-export. **The converter refuses tails instead of replaying relative TTLs/auto IDs at a new wall clock or discarding writes.** Unknown legacy shapes/commands also stop conversion.
4. Stream export file must be `{version:1, baselineSeq:N, entries:{...}}`, where N is the same frozen checkpoint. Each stream value is the actual existing `{type:"stream",value:[{id,fields}],groups:{...},expiresAt?}` format. Empty entries are valid only with independent evidence that the instance had no streams. Stream/nonstream key conflicts, incomplete groups/consumer structures, invalid IDs, duplicate members and unknown types fail validation. TTL timestamps are preserved, not extended.
5. Create operator approval JSON containing `instanceId`, `baselineSeq`, `snapshotSha256`, `aofSha256`, `streamsSha256`, `freezeConfirmed:true`, `streamsComplete:true`, and `expectedKeyCount` (the union of snapshot and complete stream export keys, including entries whose absolute TTL may expire during downtime). Compute hashes from the exact exported file bytes. These are operator attestations, not independently discovered provider facts.
6. Run locally against the exports:

   ```sh
   env -i PATH="$PATH" node scripts/convert-pdim-legacy-recovery.mjs convert \
     snapshot.json aof.json streams.json approval.json NEW_OUTPUT_DIRECTORY
   env -i PATH="$PATH" node scripts/convert-pdim-legacy-recovery.mjs verify NEW_OUTPUT_DIRECTORY
   ```

   No output directory is created on validation failure. Filesystem failure after creation leaves an incomplete directory without a valid READY record; do not upload it. Retain originals and a copy of the verified conversion on independently durable storage. Checksums detect corruption; they are not a signature against a malicious operator who rewrites approvals and digests.
7. Restore the converted generation into an isolated service/provider namespace first. Validate expected values, absolute TTL behavior, stream IDs/groups/pending state and application job/session invariants before production approval. The CLI validates structure and checkpoint identity; it does not certify external export completeness, resolve historically lost streams, or prove RPO/RTO.
8. With writers still fenced, an authorized operator uses the existing provider/fabric tooling for the correct instance owner and `redis-store` pocket to upload `snapshot.v2.json` under the exact generated `__snapshot__:migration-...` name, then `aof.v2.json` under `__aof__`, **then `manifest.v2.json` under `__recovery_manifest__` LAST**. Upload bytes unchanged. Retain original snapshot/AOF under separately inventoried immutable archive names outside the names that new runtime replaces; do not rely solely on provider overwrite history. Read back and compare every installed digest before switching processes. No upload command was executed or fabricated here; credentials and provider target are operator-owned.
9. Start only the new owner after verification, inspect validated recovery and reconcile real data before unfencing traffic. If interrupted before manifest publication, remain fenced: no new-format startup is authorized. Before any new writes, rollback is restoration of the archived original snapshot/AOF and old binary under the same fence, plus the frozen stream export rehydration procedure proved in the isolated drill. After new writes, **do not roll back to stale originals**; fence again and reconcile/export the new generation. If reliable legacy stream rehydration cannot be demonstrated, rollback is blocked and cutover must not proceed.

This supplies a real offline conversion path rather than treating legacy rejection as migration. Live export, installation, rollback drill and target validation remain explicitly blocked by task restrictions.
