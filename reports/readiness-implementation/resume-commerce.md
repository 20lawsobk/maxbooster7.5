# Resumed commerce repairs

## Implemented

- PayoutDashboard now submits integer `amountCents`, rejects excess decimal precision/nonfinite amounts, and supplies a UUID `Idempotency-Key`. `apiRequest` accepts optional headers without changing its auth/CSRF behavior. Follow-up repair persists the command before sending in owner-scoped local storage, fenced by the existing offline identity/epoch and serialized with Web Locks. Ambiguous responses retain the exact key across reloads and block different amounts. Acknowledged operation IDs remain recorded until the user explicitly confirms reviewing payout history and starts another withdrawal. Browser locking/storage failures block sending rather than falling back to an untracked command. A retry bypasses the UI's outdated available-balance precheck because the prior operation may already hold that balance.
- Replaced instant/T+0/minutes/no-fee claims with standard bank payout wording in the dashboard and withdrawal response. The legacy instant-fee endpoint now returns an explicit unsupported quote error instead of inventing a 1.5% fee. Existing endpoint URLs remain compatible.
- Canonical withdrawal history now supplies the actual dashboard fields (`amount`, `requestedAt`, `completedAt`, failure reason and provider state), currency-aware amounts and honest pending/review/cancelled states.
- Balance/history APIs preserve historical completed orders without canonical sources, royalty transactions, royalty statements, old ledger entries and prior `instant_payouts` in an explicitly nonwithdrawable reconciliation bucket. No historical credit, inferred net balance, funding claim or migration is fabricated. The dashboard displays the reconciliation warning and prior payout records. These are potentially overlapping evidence, deliberately not a summed payable.
- Reports now read new `commerce_operations` withdrawals for the requested period. Counts/status/month summaries and completed totals are partitioned by currency, with no meaningless cross-currency total. Legacy payout rows remain in a separate reconciliation export bucket excluded from canonical totals.
- Added checkout settlement-term snapshot helper and wired `marketplaceService.createOrder` to persist exact gross/fee/net beneficiary allocations in existing metadata. Settlement validates and consumes that snapshot rather than rereading changing fees/splits. Missing/malformed snapshots fail explicitly into reconciliation rather than silently choosing new legal terms. Existing merchant checkout already freezes the fee in provider metadata and was not rewritten.
- Follow-up closes the real marketplace checkout gap: both `initiatePurchase` (used by `/checkout/initiate` and `/purchase`) and `createCheckoutSession` now use a dedicated canonical checkout producer. It persists order identity, price/license snapshot and allocations before calling Stripe; serializes pending/owned purchase lookup; reuses the pending contract; sends canonical identity on Checkout Session and PaymentIntent metadata; and uses a stable per-order provider key plus session-list recovery for accepted creates with lost responses. Existing completed purchases cannot silently create another checkout. Expired sessions are explicitly cancelled locally and require a fresh purchase.
- The registered marketplace checkout webhook no longer inserts any order or reconstructs terms. It verifies the existing order/session/party/amount/currency identity and delegates to the actual marketplace fulfillment path. `payment_intent.succeeded` can fulfill the same order first; checkout/intent replays remain idempotent. Payment binding requires canonical order and party/license identity; completed/refunded replay rejects a different payment. The secondary StripeService beat handler delegates to this path; obsolete historical stem payments explicitly require reconciliation instead of inserting a fake completed order. Inspected `server/routes.ts`: its current checkout producers are subscriptions/registration, not marketplace; no unrelated shared-route edit was necessary.
- Removed all dead private legacy implementations from `instantPayoutService` and `payoutService`, including the alternate non-idempotent bank/transfer/split paths, fictional in-memory payout/receipt bookkeeping, old scheduler/receipt generation and dead unreferenced destination-charge producer. Kept real legacy webhook reconciliation handlers: historical provider events still need handling. Removed obsolete cache/import references and added explicit null-preference checks to canonical scheduled payout paths.

## Blocked / release gates

1. **Historical checkout contracts remain a reconciliation gate, not a producer gap.** Legacy sessions/orders without canonical identity and frozen terms are not backfilled at payment time. Previously purchased or pending historical records require authorized review. The newly implemented producer/webhook path is covered only through isolated fixtures, not a real Stripe checkout.
2. Historical evidence is preserved, not reconciled. Finance-approved source/provider matching and funded cutover, including overlaps/refunds/old withdrawals, remain blocked on authorized data/provider work. This change is not a backfill.
3. Report consumers must use `summary.byCurrency`; removed aggregate cross-currency `totalAmount`/unpartitioned summaries must not be reintroduced. Legacy records are excluded from canonical totals even where provider IDs overlap.
4. The historical evidence query is currently unpaginated. Production-scale pagination/export is desirable before exposing very large histories.
5. Actual browser reload/cross-tab interaction, Web Locks lifecycle, Stripe test-mode end-to-end flow, concurrency/lease/DB migration rehearsal, bank arrival/capability checks and production funding/tax review remain unperformed. Persistent command recovery is fixture-tested, not browser-certified. Users must not clear storage to bypass unresolved money commands; unsupported Web Locks/storage and unresolved declined commands fail closed and may require support reconciliation. The preexisting service typecheck suppressions are unchanged; syntax checks do not certify project types.

This report supersedes the prior commerce report's client payout/reporting gaps and its statement that all marketplace terms are chosen at settlement, only within the implemented scope above.
