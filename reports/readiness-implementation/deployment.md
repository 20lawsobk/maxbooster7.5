# Deployment implementation — release remains gated

Implemented the audit's recommended A approaches, not the alternative architectures. Source-only work with the application stopped. No workflow, app server, deployment, installation, live DB/provider operation, notification, model workload, or secret inspection was performed. No migrations were authored or applied. Protected shared files and `.replit`/Nix/package manifests/locks were not changed.

## Status by audit ID

### DEP-01 — Addressed source build omissions; release validation pending

The active `script/build.ts` now bundles the gateway and compute preflight module, builds Boosterstate from its Cargo lock, and downloads the pinned official Linux x64 Node 22.22.0 distribution. Node's archive is checked against the official versioned SHA-256 list; bootstrap provenance is written alongside the binary. Startup requires Node major 22 and rejects missing required gateway/Boosterstate executables. `.dockerignore` now includes `.node_bin`, which remains outside capsules. Image accounting includes its generated bytes. Native CI without a Nix store has zero Nix closure; a Nix-equipped environment with undiscoverable/unmeasured roots still fails.

Capsule restore sentinels now identify the manifest SHA-256, not just “a restore happened.” A newly built capsule cannot be skipped because an older generation's timestamp sentinel exists. Capsules with missing/invalid digest manifests fail. A checked corruption test leaves the prior restored contents intact.

Consumers: production build, `start.sh`, shipped capsule CLI, and CI packed build/restore. Gates: actually run the packed build on the target toolchain; verify Rust dynamic-library portability, Node/Python architecture and libc compatibility, image/disk size, source revision ↔ artifact digest provenance, and cold boot on a clean VM. No successful production build or fresh-image boot is claimed.

### DEP-02 — Addressed critical-tier race; release validation pending

Python joins Node modules and application code in critical restore. Background restore excludes Python and checks its results rather than logging unconditional success. The production start script validates the portable interpreter and imports required modules before any sidecars/cluster start, exports its exact path, and does not substitute a development venv. `pythonPath.ts` consumes that path instead of resolving a different interpreter. Existing exported bindings remain compatible with consumers.

The build creates a fresh Python directory and fails on download/install/import failure. `script/lib/pythonRequirements.py` exports the complete runtime dependency closure from the **existing** `uv.lock`, evaluates platform markers and installs only hash-verified wheels using pip `--require-hashes`. No lock file was edited. Tested export: 22 packages, including Linux uvloop and excluding Windows colorama.

Gates: cold restore delay/failed restore/import tests in the complete image; verify Python upstream archive provenance (the interpreter URL is versioned, but no independently pinned archive digest has yet been committed), startup-probe time budget, and representative audio/video operation. No model was run.

### DEP-03 — Addressed

`server/startup-probes.ts` uses one in-flight collection, publishes a deep-cloned completed generation, and retains the previous completed result during refresh. Unexpected probe rejection publishes failure. Healthy results expire after 120 seconds. `/startup`, `/ready`, `/readyz`, and other existing consumers use the same snapshot/expiry behavior; callers cannot mutate published probe data.

Isolated tests exercise concurrent refresh, ready-during-refresh, expiry, failed generation, recovery, and mutation isolation using the actual manager with dependency boundaries replaced. Production dependency timing remains a release smoke gate.

### DEP-04 — Partial: deterministic gates fixed; full release-equivalent acceptance blocked

CI now runs the packed production build, restores with the shipped Node, checks actual runtime artifacts/Python imports, runs the isolated contract tests, rejects missing output and fails the summary on a failed prerequisite. Existing integration tests intentionally remain identified as development-server tests: switching them to production start without isolated MaxCore/PDIM/DB provisioning would not create trustworthy release evidence.

The public-read load script supports `LOAD_BASE_URL`, bounds request/body completion to 10 seconds, prevents overlapping requests per simulated user, includes failed-request durations, measures nearest-rank P95/P99, and requires >0 requests, >=99% success, P95 <=500 ms and P99 <=1000 ms. Post-deployment smoke no longer accepts “degraded” readiness.

**Not complete:** packed `start.sh` cold boot plus dependency-ready routing, sidecar shutdown/rolling restart, authenticated transaction/worker workloads, spike/soak runs and required branch checks. Those require an approved isolated environment with real dependencies and representative fixtures, not the shared production Neon DB. No load or external smoke run was performed. These remain mandatory release gates, not waived by the stronger build job.

### DEP-05 — Partial: shared allocation is wired; measurement/enforcement gates remain

Both existing consumers (`cluster.ts` and `maxcoreLocalSupervisor.ts`) call the updated `computeWorkerSizing`. Effective capacity uses process CPU affinity, cgroup v2/v1 CPU quotas and memory limits, bounded by physical RAM. Overrides must be integral and fit the computed pool; they cannot bypass limits.

**Revised following the 4-CPU/8-GiB compatibility review:** removed the old 4.5/6-GiB per-worker tier estimate from both cluster and start preflight. It was not measured application RSS and incorrectly rejected the current runtime. Allocation is now minimum-first: reserve 20% OS/extraction headroom (at least 512 MiB), 768 MiB app primary RSS, 256 MiB MaxCore coordinator RSS, 512 MiB gateway/Rust/sidecar RSS, 1024 MiB local Python, then minimum 1024 MiB app-worker and 768 MiB MaxCore-worker RSS. Only the remaining surplus is split 70/30 between app/MaxCore. Every enabled role remains allocated; no subsystem is silently disabled or assigned zero workers.

At the reported cgroup limits (`memory.max=8589934592`, `cpu.max=400000 100000`) this admits one app worker and one MaxCore worker, retains Python, and allocates exactly within 8192 MiB including headroom. Tests verify this exact profile. App allocation is 2564 MiB (1538 MiB V8 heap), MaxCore worker 1429 MiB (857 MiB V8 heap), Python 1024 MiB, app primary 768 MiB (512 MiB V8 heap), MaxCore coordinator 256 MiB (153 MiB V8 heap), sidecars 512 MiB and headroom 1639 MiB. Heap caps leave native-memory space inside each RSS allocation, rather than inflating small allocations. Primary and app worker caps consume the same allocator output in `start.sh` and `cluster.ts`.

Role configuration (positive MiB values): `APP_PRIMARY_MEMORY_MB`, `MAXCORE_PRIMARY_MEMORY_MB`, `SIDECAR_MEMORY_MB`, `PYTHON_MEMORY_MB`, `APP_WORKER_MIN_MEMORY_MB`, `MAXCORE_WORKER_MIN_MEMORY_MB`; `COMPUTE_HEADROOM_PERCENT` is positive and below 100. Defaults above are **configurable reservations, not newly claimed measurements**. Worker counts still use validated `CLUSTER_WORKERS` / `MAXCORE_LOCAL_CLUSTER_WORKERS` overrides. Invalid/oversized minima fail before sidecars spawn. A 2-GiB quota with default minima is infeasible; a tested 4-GiB/2-CPU configured small profile remains possible. Fractional CPU shares time-share one worker per role instead of inventing a four-core physical minimum. At four effective CPUs each local role has one CPU share; smaller quotas retain one concurrency slot per role and share the actual cgroup CPU ceiling.

These are allocation estimates, **not per-process enforced RSS limits**. The prior reported ~3-GiB total working RSS is useful compatibility context, not peak-load certification. The outer cgroup enforces aggregate memory/CPU, allocator accounting prevents assigning overlapping memory budgets, and Node heap limits constrain V8 only. Supported machine classes still need load/soak certification. Nested/custom cgroup mounts, extraction disk/RSS peaks, native/Python peak demand, CPU saturation and OOM/latency behavior remain unmeasured.

AI/runtime owner now owns the supervisor cap integration (not silently assumed complete here). `computeWorkerSizing` exposes `workerHeapMB`, `workerMemoryMB`, `primaryHeapMB`, `maxcorePrimaryHeapMB`, `pythonMemoryMB`, `pythonThreads` (1), `cpuBudget` and `reservationsMB`; `freeMemGB` remains the allocated worker role pool, not available host RAM. Use `nodeSizing.workerHeapMB` for each MaxCore Node worker's V8 cap, `maxcorePrimaryHeapMB` for its separately reserved coordinator, and `nodeSizing.pythonThreads` for BLAS/OpenMP thread variables, validating the Python runtime honors them. The coordinator must not inherit a full worker heap on top of the worker pool allocation. Child RSS still needs process/cgroup enforcement or admission control once measured. Do not treat modeled HyperGPU lanes as physical memory/thread enforcement. No MaxCore source was edited by this domain.

**AI/runtime integration follow-up (implemented by AI/media owner):** supervisor now sets separate limits: coordinator allocation is divided between the TSX launcher and nested primary; `MAXCORE_NODE_WORKER_HEAP_MB=workerHeapMB` is consumed by the nested Node entrypoint's resource-only `cluster.setupPrimary` exec arguments. Inherited heap overrides are removed. Native child BLAS/OpenMP/NumExpr/BLIS/vecLib pools, nested libuv pool, Uvicorn worker count and MaxCore process-stream count are capped at one; HyperGPU modeling uses Python's assigned thread count. Existing Python spawn preserves these caps. Five isolated resource/dead-code tests pass, including execution of the actual nested worker-heap setup. No startup/lifecycle redesign or allocator edits were made by that owner. With `maxcorePrimaryHeapMB=153`, launcher and primary each receive 76 MiB; validate cold/peak use rather than claiming this small heap is measured sufficient. Native/Python RSS and outer cgroup acceptance remain open. Details and subprocess-render cancellation tests are in `ai-media.md`.

### DEP-06 — Addressed recurring-attempt deadline defect; operational acceptance pending

`server/instrument.ts` tracks an immutable first heartbeat attempt; retries no longer postpone the first-success silence deadline. Once delivery recovers, age is measured from last success. Threshold is inclusive at 24 hours. Existing independent alert dispatch is awaited so asynchronous delivery failure reaches its error handler. Existing readiness consumers receive corrected silence age.

Tests simulate 25 hours of failed delivery, recovery, then another 25-hour outage. Restart policy is explicitly a new per-process 24-hour first-attempt grace (first attempt is scheduled 15 seconds after monitor start). **No cross-restart persistence is claimed.** Frequent restarts can extend detection; independent uptime/monitoring coverage must address this before release. SDK `flush` is the existing transport-drain signal, not proof of remote event indexing. Staging must verify actual Sentry receipt, real independent page delivery at the configured deadline, and restart-during-outage behavior. No alert was sent.
