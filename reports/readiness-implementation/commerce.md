## Main implementation surfaces

- Unapplied `migrations/0022_commerce_webhook_receipts.sql` and `migrations/0023_commerce_settlement.sql`: permanent receipts/inbox, sources, allocations, journals/entries, operation leases, payout draws, schedules and statement details. Journal entries are append-only and balance is checked with a deferred trigger.
- `server/services/commerce/`: repository, orchestration, Stripe adapter, payment verification, payout consumers, settlement, compensation, statement funding, entitlements and merchant integrations.
- Existing marketplace, Stripe, instant/scheduled payout, royalty, billing and webhook consumers now delegate to these implementations. Private legacy methods retained in several services are not the primary money-moving consumers.
- New physical-merch settlement withholds actual Stripe-calculated tax; configured shipping proceeds form part of seller proceeds. Full reversals release recorded tax liability; partial goodwill refunds do not fabricate a tax reversal. Tax remittance and jurisdictional reversal obligations still require provider/finance approval.

## Concrete cross-owner integration / release gates

1. **Apply and validate migrations only with explicit authorization.** Resolve migration numbering/registration alongside other domains; other files also use numeric prefixes 0022/0023. Confirm prerequisite order/revenue uniqueness constraints. Exercise PostgreSQL concurrency, deferred journal balance checks, crash recovery and lease races in an approved isolated database before release.
2. **Client payout contract needs coordination.** The existing PayoutDashboard submits `{amount,currency}` while the endpoint expects `{amountCents,currency}` and `Idempotency-Key`. Generate one command key per intentional withdrawal, reuse it across retries, and send the exact minor-unit amount. The shared `apiRequest` helper currently has no arbitrary-header option; the owner must add header support or coordinate a validated body-key transport. Do not expose this flow as ready until corrected. Refund callers likewise need a stable idempotency key.
3. **Historical reconciliation is separate.** Review old balances, completed orders, withdrawals, statements and provider identities before any approved migration into this ledger. The new engine does not infer credits from old gross-sale analytics or assume missing history equals paid cash.
4. **Actual provider configuration is required.** Verify Connect transfer/payout capabilities, connected-account manual payout scheduling (to avoid automatic payout races), settlement currencies, account ownership, funding permissions, and event subscriptions. FX settlement requires an explicit conversion journal; it is rejected rather than silently converted.
5. **Physical merchandise configuration:** `STRIPE_MERCH_SHIPPING_RATE_ID` must identify a real active USD fixed shipping rate; `STRIPE_MERCH_SHIPPING_COUNTRIES` lists its approved destinations. Stripe Tax registration/product classification must be configured. Growth migration 0093 and its exported checkout/event contract are prerequisites. Checkout shipping addresses are persisted from Stripe's verified collected shipping details. Growth must review shipping-address consumer compatibility and physical fulfillment suspension during disputes (its event contract currently represents paid/expired/refunded, not disputed).
6. **Finance review lanes remain explicit.** Overlapping bank returns and refund recoveries require reconciliation of real cash locations before release. Legacy balances, unsupported rails and currency conversion must not be bypassed by generated balances, simulated payouts or guessed provider responses.
7. **Production verification remains unperformed.** Perform authorized test-mode checkout→license/merch fulfillment→beneficiary balance→withdrawal→bank outcome→refund/dispute/return drills, worker/inbox scheduling checks, fiscal validation, and UI integration testing. No claim of production readiness follows from syntax or isolated tests alone.
