---
name: Deployment autofix system coverage gaps
description: Two structural blind spots found in scripts/deployment-autofix.mjs's error coverage, plus the confirmed root cause of a string of build failures.
---

## Scope boundary: the autofix system never sees `npm run build` itself

`scripts/deployment-autofix.mjs` (the fail-closed pre-build gate) only classifies
TypeScript diagnostics, ESLint rules, Drizzle schema drift, import resolution,
and runtime health probes — all captured in `scripts/error-fix-configuration.json`.
It runs entirely BEFORE the real `npm run build` (script/build.ts: vite build →
esbuild server/cluster bundles → optional portable-Python provisioning → capsule
packing via script/lib/capsulePack.ts). Nothing in that later stage is classified,
retried, or diagnosed by the autofix/research-catalog system — a failure there
(bundler error, network failure fetching the Python runtime, a capsule pack
error, or the deploy platform's own image-size check) surfaces as a raw
platform-level error message with zero autofix help.

**Why:** confirmed via `listDeploymentBuilds`/`getDeploymentBuild` build-log
history — 3 of 4 consecutive failed deploys (2026-08-28/29) died at the
platform's post-build image-push step with `image size is over the limit of
8 GiB: total size of layers exceeds limit`, a failure mode with no entry
anywhere in `error-fix-configuration.json`'s `runtimeAndInfra` section and no
code path in `deployment-autofix.mjs`/`fix-all.mjs` that could have caught it
before the platform did. Root cause was capsule packing using gzip-9 (much
worse ratio) instead of the intended zstd-19; a same-day commit
(`Compress deploy capsules with zstd instead of gzip-9`) fixed the immediate
size problem, but the systemic gap — build-stage errors have zero autofix
coverage — remains open.

**How to apply:** when asked to assess or extend the deployment autofix
system's coverage, remember its stated scope stops at the pre-build gate; the
bundler/capsule-pack/image-size class of failure needs its own detection (e.g.
a `runtimeAndInfra` entry for "deploy image size" / "build command failure",
or a pre-flight capsule-size check in script/build.ts) — it will not be caught
by expanding `typescriptDiagnostics` or ESLint mappings.

## The TS-diagnostic coverage self-check reads a stale, hand-refreshed snapshot

`scripts/validate-error-research.mjs` (the script that lets the autofix gate
claim "N families cover the live error surface") diffs
`error-fix-configuration.json`'s `typescriptDiagnostics` keys against
`reports/fix-all/tc-server-current.txt` / `tc-client-current.txt` — static
files last regenerated by hand, not by a live `tsc` run at validation time.
As of 2026-08-29 these were ~24 days stale (last touched 2026-08-05).

**Why:** a fresh, currently-passing `npm run check:server`/`check:client`
happened to match the stale snapshot's code set exactly, so there is no
live discrepancy today — but the mechanism itself cannot detect a genuinely
new diagnostic code introduced after the snapshot's last manual refresh. The
real per-deploy `tsc` gate (`fix-all.mjs`'s `verify` phase, writing
`tc-server.txt`/`tc-client.txt`) would still correctly block an unresolved
error regardless — this gap only means such an error was never "researched"
ahead of time, not that it would slip through undetected.

**How to apply:** if asked to make the coverage self-check trustworthy, have
`validate-error-research.mjs` run its own fresh split typecheck (or read
`fix-all.mjs`'s freshly-written `tc-*.txt`, not the `-current.txt` files) at
validation time instead of a committed snapshot.
