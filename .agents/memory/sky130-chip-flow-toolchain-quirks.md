## volare silently 401s if a GitHub integration token is present
`volare` (the sky130 PDK version manager) calls the public GitHub API to list/fetch PDK releases. If the repl has a GitHub integration installed, its `GITHUB_TOKEN`/`GITHUB_PERSONAL_ACCESS_TOKEN`/`GITHUB_PAT`/`GITHUB_REPO` env vars get auto-picked-up by generic HTTP tooling and sent as auth — but a token scoped to the user's own repo(s) is not valid for volare's public PDK-release API calls, so requests 401 instead of falling back to anonymous access.

**Why:** volare has no code of its own that reads these vars deliberately; some underlying HTTP client/library defaults to using any ambient GitHub credential it finds.
**How to apply:** run volare commands with those vars stripped, e.g. `env -u GITHUB_TOKEN -u GITHUB_PERSONAL_ACCESS_TOKEN -u GITHUB_REPO -u GITHUB_PAT volare enable ...`, so it falls back to anonymous public GitHub API access. Never print/inspect the token values themselves while debugging this.

## Double-backgrounding kills the task before it starts
Passing `run_in_background: true` to a shell-exec tool call AND ALSO appending a trailing `&` inside the script body is not redundant-but-harmless — it silently orphans/kills the real command before it produces output. The wrapper exits 0 immediately, no log file or process appears, and the thing you meant to background (e.g. a large PDK download) never actually ran.
**Why:** the outer tool already backgrounds the whole script; adding an inner `&` backgrounds a child of a process that the outer mechanism may tear down immediately since it considers the (empty) foreground command already finished.
**How to apply:** background at exactly one layer — either the tool's `run_in_background` flag, or a trailing `&`, never both. If a background download/build produces no log and no process, suspect double-backgrounding first.

## One real typo in the sky130 PDK's own verilog cell library breaks Icarus Verilog
`libs.ref/sky130_fd_sc_hd/verilog/sky130_fd_sc_hd.v` (as fetched via volare) has exactly one line — an `` `endif GUARDNAME`` closing a `` `ifndef SKY130_FD_SC_HD__LPFLOW_BLEEDER_FUNCTIONAL_V`` — missing the `//` that all 3100+ other endif/else guard-name comments in the same file have. Icarus Verilog's preprocessor cannot parse a bare trailing identifier after `` `endif`` and throws a hard-to-diagnose syntax error deep in the file (tens of thousands of lines past the real cause), preceded by a wall of unrelated "macro UNIT_DELAY undefined (and assumed null)" warnings that are a red herring (defining `-D UNIT_DELAY=#1` does NOT fix it).
**Why:** confirmed via `grep -c` that this exact bare-trailing-identifier pattern occurs exactly once in the file, vs 3100+ correctly-commented instances — a genuine isolated vendor typo, not a systemic incompatibility.
**How to apply:** for iverilog-based gate-level simulation, never edit the installed PDK in place. Make a private sanitized copy (e.g. `flow/sim_models/sky130_fd_sc_hd.sim.v`) with only that one line patched (add `// ` before the trailing guard name), and point the simulator at the copy. Yosys synthesis itself is unaffected since it reads the `.lib` file, never this `.v` behavioral model.

## `repair_timing` does not re-legalize; unlegalized inserted cells fatally break detailed routing later
`repair_timing -setup` / `-hold` insert, clone, and resize cells using the resizer's own fast heuristic placement, not a real legalize pass. If you don't call `detailed_placement` (+`check_placement`) again immediately after each `repair_timing` call, the newly-added cells can be left off the site/row grid or overlapping neighbors. This doesn't show up as an error at the CTS/placement stage — timing reports look fine — but many stages later, `detailed_route` (TritonRoute) fatally errors with `[ERROR DRT-0073] No access point for <cellname>/<pin>` for exactly those cells (recognizable by resizer-generated names: `rebufferN`, `cloneN`, `holdN`), aborting the whole routing run.
**Why:** confirmed directly — every one of 73 DRT-0073 failures named a `rebuffer*`/`clone*`/`hold*` instance (the exact categories `repair_timing -setup`/`-hold` create), none named an original synthesized cell. Adding `detailed_placement`+`check_placement` right after each `repair_timing` call (not just once, before both) made the failures disappear on rerun with otherwise-identical scripts.
**How to apply:** in any OpenROAD flow, treat `repair_timing`/`repair_design` calls as needing their own trailing legalize, the same way placement itself does — legalize after every timing-repair call, not just once before the repair sequence starts.

## `global_route`'s "hard congestion benchmark" extra pass looks identical to a hang
After normal congestion-removal iterations, `[INFO GRT-0101] Running extra iterations to remove overflow.` can escalate to `[INFO GRT-0103] Extra Run for hard benchmark.` and then print nothing further for 10+ minutes while still holding ~100% CPU on a real ~84K-cell design. This is indistinguishable from a stalled/hung process by log output alone.
**Why:** unconfirmed whether it would have eventually finished on its own (killed at ~21 min with no new output for ~12 min) — but a second attempt with `-allow_congestion` passed on the identical design in a comparable time budget, reporting `[WARNING GRT-0115] Global routing finished with congestion` and proceeding normally into detailed route.
**How to apply:** pass `-allow_congestion` to `global_route` on any real (non-toy) design so it terminates by accepting/reporting residual congestion instead of exhaustively fighting to fully eliminate it; treat a long silent "hard benchmark" run as ambiguous rather than assuming either "definitely hung" or "definitely fine" — CPU still pegged at ~100% is the one signal that distinguishes it from a true deadlock.

## Yosys `check -noinit` can report false-positive "no driver" on port wires
After a full `synth -flatten` -> `dfflibmap` -> `abc -liberty` -> `clean -purge` flow, `check -noinit` reported "used but has no driver" for several real output ports (a registered output and two combinational read-port outputs) even though the design was logically complete and non-trivial (tens of thousands of real cells). The written `write_verilog` netlist showed these exact signals correctly connected to real cell outputs (e.g. `.Q(the_signal)`).
**Why:** `write_verilog`'s own backend prep passes (BMUXMAP/DEMUXMAP) run strictly after `check`, and appear to perform additional port-to-driver wire canonicalization that `check` at that point in the flow doesn't yet see — i.e. the warning reflects a transient/intermediate netlist state, not the final one.
**How to apply:** don't trust a `check` "no driver" warning on ports as ground truth by itself when the design is otherwise large/real (as opposed to the classic degenerate-netlist case). Confirm with an actual gate-level simulation of the written netlist (real cell behavioral models) reproducing the RTL-level testbench's pass/fail results — that is definitive; log warnings at intermediate stages are not.

## `-single_step_dr` is a dev-only internal flag, not a safe checkpoint mechanism
TritonRoute's `detailed_route` accepts an undocumented `-single_step_dr` argument, visible only by reading its Tcl source, never in `-help` output. The source comment marks it as intended for algorithm development, explicitly not a user option, and intentionally left out of the help string.
**Why:** an internal/dev-only flag with no help-string presence has no stability or correctness contract for external use — a plausible-looking "step through routing one iteration at a time" flag is not evidence it's a supported resume/checkpoint API.
**How to apply:** never adopt a tool behavior discovered only by reading its source (comments, hidden args); if `-help`/official docs don't surface it, treat it as unsupported. This is also a copyright/IP boundary: read a third-party tool's source only to confirm how to correctly call its public interface, never to copy its implementation or lean on undocumented internals as if they were a contract — learn from public behavior, build the actual thing yourself.

## Latest GitHub source is not authoritative for an already-installed tool version
OpenROAD's GitHub master shows `-bottom_routing_layer`/`-top_routing_layer` as deprecated (hard error if passed), but the installed build here (`2.0-unstable-2025-03-01`) runs a script that passes both flags successfully — proof the installed version predates that deprecation.
**Why:** open-source EDA tools installed via Nix/volare can be many months to a year+ behind upstream master; reading current GitHub source to infer a locally-installed binary's flag semantics is only valid until proven otherwise.
**How to apply:** trust empirical behavior of the actually-installed binary (a real run, or its own `-help` output) over upstream source when they conflict. A script already proven working in this sandbox outweighs newer upstream documentation.

## Sectioning global_route + detailed_route into independently checkpointed processes
Splitting the monolithic route stage into (a) an isolated `global_route` process that reads the CTS checkpoint and writes its own `.odb`, and (b) `detailed_route` invoked repeatedly as separate processes — each bounded by a small `-droute_end_iter`, reloading the previous section's `.odb` and writing a new one — resets peak memory between processes and bounds an interruption's blast radius to one small section instead of the whole run.
**Why:** OpenROAD has no supported mid-run checkpoint for detailed routing (see `-single_step_dr` above), so the only safe pause points are between whole `detailed_route` invocations, which only exist if the flow is restructured to call it repeatedly instead of once.
**How to apply:** the very first `detailed_route` call on a fresh global-route checkpoint still has to route every net for the first time — this initial pass is one atomic, non-interruptible block regardless of `-droute_end_iter`, so sectioning reduces risk for iterations after the first, not for that unavoidable first pass.

## A whole OpenROAD PnR flow can silently run single-threaded despite a multi-core box
None of this flow's stage scripts ever passed OpenROAD's own `-threads` CLI flag (confirmed present via `openroad -help`: `-threads count|max`). On a 4-vCPU container, a live detail-route process showed `Threads: 4` in `/proc/<pid>/status` (OpenROAD spawns a handful of OS threads regardless) but only ~99% aggregate CPU in `ps aux` the entire time — i.e. the actual parallel algorithms (pin access, track assignment, TritonRoute's worker-based routing) were computing on one effective thread. Passing `-threads 3` on an otherwise-identical rerun produced ~290-300% aggregate CPU immediately and cut the single biggest historical bottleneck (pin access: previously 38+ min of wall-clock and still not finished) to 13m48s wall-clock end-to-end (cpu time 41:21, i.e. ~3x realized parallel efficiency, near-perfectly matching thread count) — for peak memory of 845MB vs the old single-threaded run's ~740MB at a comparable point, i.e. the speedup was nearly free memory-wise, not a tradeoff.
**Why:** `ps aux`'s %CPU column is a real aggregate-across-threads number on Linux, not per-thread — ~99% with `Threads: 4` present is definitive proof the heavy algorithmic work itself is single-threaded, since true 4-thread saturation would show ~400%. Thread *existence* (a nonzero OS thread count) and thread *utilization* (the flag actually handed to the tool's parallel algorithms) are different facts; only the CLI's own `-help` (not GitHub source, per the copyright/undocumented-internals boundary) confirmed the real lever (`-threads`).
**How to apply:** for any OpenROAD-based flow, always pass `-threads <n>` explicitly on every stage invocation (or build a single wrapper that does it for every stage) — never assume a multi-core box is being used just because the process shows multiple OS threads. Deliberately leave at least one core of slack (e.g. `n-1`, not the literal max) rather than fully saturating cores, as a hedge against per-thread memory scaling being unmeasured for a new design — verify actual peak RSS growth empirically (see next entry) before pushing to full core count.

## No GNU `/usr/bin/time` in this sandbox — use the kernel's own VmHWM for real peak-RSS instead
`/usr/bin/time -v` (which gives "Maximum resident set size" + wall-clock + %CPU in one line) is not installed here. `/proc/<pid>/status`'s `VmHWM` field is a kernel-maintained, monotonically-non-decreasing high-water-mark for that process's whole life — a single read of it at (or near) process exit gives the same true peak that `time -v` would, with no need for tight continuous polling; a background loop sampling it every few seconds and keeping the max is sufficient and dependency-free.
**Why:** confirmed `/usr/bin/time` absent via `which time`/direct invocation (`No such file or directory`); VmHWM behavior (never decreasing, kernel-tracked) is documented `/proc` behavior, not guessed.
**How to apply:** for any "how much memory did this actually use" question in this environment, poll `VmHWM` (not `VmRSS`, which is only the *current* value and can under-report a since-passed peak) rather than reaching for `time -v` or installing a new package for it.

## A visible "does the checkpoint exist yet?" existence-check reads as an error to someone watching the raw terminal
When following the user's own preference for transparent (non-silent) progress monitoring — running `ls <expected-output>.*` in the foreground to poll whether a section finished — an expected-negative `ls: cannot access ...: No such file or directory` (because the job legitimately hasn't reached that save point yet) is visually indistinguishable, to someone reading only the raw pasted terminal output, from a real missing-file bug. It generated a genuine "there's missing files" bug report from a screenshot of otherwise-normal polling output.
**Why:** raw tool output shown for transparency has no inline framing — the same string means "still working, nothing wrong" mid-run and "something is actually broken" post-completion, and a reader without the full run context can't tell which.
**How to apply:** when deliberately showing a not-yet-true existence check for transparency, label it inline (e.g. echo `"(expected empty until iteration N completes)"` right before/after the `ls`) so raw output can't be misread out of context; if a user reports an error that looks exactly like a routine polling line, check whether it's your own progress-check output before assuming a real regression.
