---
name: Dependency-graph concurrent scheduler traps
description: Two non-obvious correctness bugs to avoid when building/modifying a dependency-driven multi-lane graph executor with shared-tensor lifecycle tracking
---
- Trap 1 — memory lifecycle must use live consumer-countdown, not precomputed last-consumer-by-index: when freeing an intermediate tensor as soon as its last consumer finishes, "last consumer" cannot be decided upfront by scanning topological order (e.g. "the last node in order that reads this handle"), because lanes complete out of order under real concurrency. A later-in-order consumer can finish before an earlier-in-order one. Must decrement a live per-tensor consumer count as each consumer actually completes, and free only when it hits zero.
- Trap 2 — a Future-keyed-by-name wait must check shared failure state under the SAME lock before creating/waiting on the future, not just at the top of the function: if lane A fails and records the error, then lane B calls `get_future("A's output")` for the first time, B must see the recorded failure and raise immediately — not create a fresh, never-to-be-resolved Future and block on it forever. Checking `errors` only before the lock, or only for already-existing futures, reopens the deadlock for that ordering.
- **Why:** both bugs are invisible in simple/serial tests and only surface under real concurrent completion-order variation or failure-during-wait races — exactly the cases a scheduler exists to make safe. Found while building `external/maxcore/.../ai_model/maxcore/runtime/scheduler.py` + `engine.py`'s memory bookkeeping; proven by tests that force out-of-order completion and inject failures mid-wait (`tests/test_gpu_native_orchestration.py`).
- **How to apply:** if you touch either the per-tensor free-on-last-consumer bookkeeping or the cross-lane Future/error-propagation path in a dependency-graph executor, re-run (or write) a test that forces genuinely out-of-order lane completion and a failure-during-active-wait, not just a happy-path DAG.
