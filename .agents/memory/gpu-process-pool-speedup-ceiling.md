---
name: GPU multi-stream process-pool speedup ceiling
description: What was actually achieved (and not achieved) redesigning thread-based multi-stream GPU orchestration into a process-pool + shared-memory path, and what would be needed to go further.
---

For a CPU-only "digital GPU" backend whose real compute is NumPy/BLAS-bound, CPython's GIL makes thread-based multi-stream concurrency (a plain thread pool/scheduler dispatching independent graph branches to worker threads) a **guaranteed wall-clock loss** (measured 0.12x-0.35x of serial time on a 4-core container) -- there is no thread-count or tuning fix for this while the hot path is Python/NumPy bytecode holding the GIL.

Replacing the thread pool with a persistent, spawn-context **process pool** (one long-lived OS process per lane/stream, reused across `run()` calls) removes the GIL constraint entirely (each process has its own interpreter), but introduces two new costs that eat most of the theoretical win:
1. **IPC/serialization overhead** -- pickling NumPy arrays through a multiprocessing queue for every cross-lane value. Fix: a persistent shared-memory arena (bump-allocator, sized to ~2x the run's reserved bytes or prior high-water mark, grown-not-shrunk across runs) that lanes write/read via `multiprocessing.shared_memory`, falling back to pickling only when a value doesn't fit or isn't shm-eligible.
2. **BLAS thread oversubscription** -- if each of N worker processes' NumPy still uses the system's full multi-threaded BLAS, N processes x M threads oversubscribes the container's actual core count. Fix: pin each worker to 1 BLAS thread via env vars at process spawn.

**Result actually achieved** (both fixes applied, measured with the project's own orchestration benchmark across many repeated runs to separate signal from this container's substantial scheduling noise): moved the best-case configuration (num_streams == physical core count, matrix sizes roughly 512-1536 per side) from a *guaranteed* loss to **near-parity / coin-flip** (medians ~0.85-1.0x of serial, means ~0.97-1.0x, a real fraction of individual runs >1x, some up to ~1.4-1.6x) -- genuinely better, but NOT a reliably-provable win. Bigger payloads (2048+ per side) got *worse* again (inter-process memory-bandwidth contention outweighs amortized overhead), and mismatching num_streams to physical core count (fewer streams than cores, each then given multiple BLAS threads) measured worse than 1 BLAS thread x 1 process per core.

**Why the ceiling exists**: process/IPC dispatch has an inherent fixed cost per `run()` call that no transport optimization removes, and concurrent processes on the same box compete for memory bandwidth, not just CPU. Getting a *reliable* (not coin-flip) win likely requires sidestepping IPC entirely: a native/C-extension (Cython/Numba `nogil`) compute kernel that releases the GIL for its full duration, run on real OS **threads** (shared memory for free, no process-spawn or IPC cost, no per-process BLAS-pinning tax) -- the option a from-process-pool redesign does not pursue and would need a separate implementation effort.

**Benchmark-noise methodology**: this container's wall-clock timing is noisy enough that even a "stable" single-process (no multiprocessing) benchmark can swing 70%+ between back-to-back runs, and one-off outliers (e.g. a single run showing a huge apparent regression) can fail to reproduce across 3+ immediate re-runs. Before concluding a measured slowdown is a real code regression, re-run the exact same computation several times in fresh processes; if the outlier doesn't reproduce, it's environment noise, not a regression, and any regression-detection gate for such benchmarks needs a much wider tolerance than a typical single-process/no-IPC benchmark.

**How to apply**: don't re-attempt a pure-Python thread-based speedup for NumPy-bound kernels -- it's a proven, structural dead end on CPython. Don't expect a process-pool path to ever beat serial by a wide, reliable margin without also removing IPC (native GIL-releasing kernels) -- benchmark honestly and report a range/median from repeated runs, not a cherry-picked single run.
