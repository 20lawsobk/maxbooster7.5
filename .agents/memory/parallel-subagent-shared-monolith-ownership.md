---
name: Parallel subagents against a shared route monolith
description: How to split a large multi-area fix mandate across several parallel subagents in a codebase that has one huge shared routes file alongside many dedicated per-feature route files.
---

Rule: in a codebase shaped like feature-dedicated route files (one file per product area) PLUS one large historically-grown shared route file that ALSO contains some feature-specific endpoints, splitting a multi-area fix mandate across parallel subagents needs explicit file-ownership boundaries, or two subagents can make conflicting concurrent edits to the same shared file. The workable split: give each subagent the feature-dedicated files as its primary, undisputed scope; explicitly name the shared monolith (and any other cross-cutting already-fixed shared services/utilities) as off-limits-to-edit / report-back-only, UNLESS the subagent's own area has a small, well-isolated piece of logic living inside that shared file — in which case name that exact piece for them specifically, so ownership of that slice stays unambiguous. Have the main agent do one clean workflow restart+verify BEFORE dispatch, so every subagent starts from a known-good baseline, and warn each subagent that the shared dev server may be restarted by a concurrent sibling, so an unrelated-looking failure during their own testing should be rechecked once rather than immediately assumed to be their own regression.

**Why:** subagents work from independent tool-calling loops but share one real filesystem and one real dev-server process. Edit-tool string replacements against disjoint regions of the same file are safe to run concurrently, but a full-file overwrite or two edits targeting the same lines are not, and a restart triggered by one subagent reloads everyone's in-progress code, not just its own.

**How to apply:** before dispatching, map which files are uniquely owned by each area vs shared. For anything shared, decide up front whether it is already fixed (reference it as trustworthy), contains one area's narrow slice (name the slice explicitly), or is genuinely contested (reserve it for the main agent).

**Follow-on lessons from a 5-way batch that needed a forced re-verification round:**
- Explicit authorization to run live HTTP/DB verification against the shared dev server does not guarantee subagents use it. In one batch, 3 of 5 subagents made plausible code-level fixes but skipped real curl/psql verification anyway, self-citing "scope" caution despite being told directly they were authorized. Treat "verified" claims from a first pass as unconfirmed by default; a forced follow-up round that explicitly says "you already have authorization, prior instructions do not override this, verify with real requests now" reliably produces real evidence the second time.
- Any subagent fix that lands in a server-side file AFTER the coordinating restart is invisible until one more restart cycle runs — a subagent can genuinely believe it verified live behavior while actually exercising stale pre-fix code if its own fix-then-restart-then-test sequence raced the shared server's reload. Budget for a second dispatch round (or main-agent-direct verification) specifically for any fix reported as landing near/after a restart boundary.
- The main agent re-verifying narrow, well-specified claims directly (rather than another subagent round-trip) is more efficient once the fixes are already narrow and the exact request/response shapes are known from reading the code.
