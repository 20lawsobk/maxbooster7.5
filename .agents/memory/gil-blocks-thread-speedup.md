---
name: GIL blocks thread speedup for NumPy-bound compute
description: Why the digital-GPU runtime's multi-stream scheduler defaults to serial (num_streams=1) instead of cpu_count, with the measured evidence
---
- Rule: a correct, deadlock-free, dependency-driven thread scheduler (external/maxcore/.../ai_model/maxcore/runtime/scheduler.py) does NOT imply thread concurrency will speed up the work it schedules. Never default a `num_streams`/worker-count knob to `os.cpu_count()` for a backend whose nodes are mostly NumPy/Python-level (tiling, padding, masks) between brief native calls — benchmark first.
- **Why:** measured on this project's own SiliconSimtEngine-backed GEMMs (4-core container, generic nixpkgs BLAS), thread-based concurrency was slower than serial at every size tested — 0.12x at small independent GEMMs (8x, 96x256@256x96), 0.35x at large ones (4x, 1024x1024@1024x1024). A direct GIL probe confirmed NumPy's `@` releases the GIL for only part of a call's wall time; thread-scheduling/GIL-handoff overhead ate the rest. Raw ad-hoc numpy-only threading (no engine/scheduler overhead) showed a narrow ~1.1x window only around ~2048-dim mid-size gemms and was a net loss everywhere else on this hardware — not a reliable, exploitable default.
- **How to apply:** keep `num_streams` (or equivalent) defaulting to 1/serial; make concurrency an explicit opt-in (env var or constructor arg) once a caller has benchmarked their *own* node workload. If real parallel speedup is later needed, the fix is a different concurrency model (process pool / native GIL-releasing extension), not tuning the thread count — see `tests/benchmark_gpu_native.py::bench_stream_overlap_small/_large` for the standing regression/characterization harness, which sweeps sizes and reports the crossover honestly rather than asserting a speedup.
