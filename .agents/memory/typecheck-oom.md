# Full-project typecheck: OOM vs. slow

The `typecheck` workflow (`tsc --noEmit` over client+shared+server) is extremely heavy on this monorepo.

- With the **default Node heap** it OOMs around ~4GB and crashes — historically this also starved tsx and could take down the running app at boot.
- With **`NODE_OPTIONS=--max-old-space-size=6144`** it does **not** OOM, but a cold full check runs **very slow (>9 min, no output until the end)** and drives container memory to ~97% (7.7/7.9GB) when run **alongside** the `Start application` workflow — at which point the app's `/api/ready` starts timing out.

**Fix applied (current):** the one monolithic `tsc` is split into two per-area programs that share `tsconfig.json` as a base — `tsconfig.server.json` (server + shared + root `*.ts`) and `tsconfig.client.json` (client/src + shared), each with its own `tsBuildInfoFile` so the incremental caches don't clobber each other. `npm run check` runs both; `check:server` / `check:client` run one. The `typecheck` workflow runs `npm run check` at `--max-old-space-size=4096`, idle (autoStart off). `extends` REPLACES `include`/`exclude` (does not merge) — so each sub-config restates them.

**Incremental cache must live OUTSIDE `node_modules`.** The build-info files are in `.cache/tsbuildinfo.{server,client}` (`.cache/` is gitignored). The original config put the buildinfo at `./node_modules/typescript/tsbuildinfo` — but the post-merge step runs `npm install`, which can wipe `node_modules/typescript`, resetting the incremental cache and forcing a slow **cold** whole-program run every time. With the cache in `.cache/`, only changed files (+ their dependents) are re-checked on subsequent runs.

**Whole-program scope is required; per-diff checking is not sound.** A typecheck must consider the whole program because a change in file A can break a *dependent* B that isn't in the diff. So the gate's *scope* is the whole program by necessity — but the *work* is changed-files-only once the incremental cache is warm. Diff-only tools (e.g. `tsc-files`) pull in named files + their imports but NOT their dependents, so they can pass while the real build is broken — fine as a local hint, wrong as a gate. The split also lets you scope by area: if you only touched server code, run `check:server`.

**Why split instead of just bumping heap:** each half is a much smaller program, so peak RSS drops to ~3.46GB per half (measured, standalone) — well under the ~4GB default-heap OOM ceiling. So 4096 is generous headroom (was 6144 for the monolith). server↔client are independent (server imports nothing from client; the only "client" hit was `openid-client`); `shared` is included in both (checked twice, but it's tiny: 51 files).

**Why NOT combine the typecheck into the app's run command (`npm run dev`):** memory is ADDITIVE, not shared. The dev app is long-lived at ~4GB; a typecheck spikes ~3.4GB. Co-resident = ~7.4GB in an ~8GB box = guaranteed OOM (this is the exact crash). A check must also run→report→exit (gate semantics) while the app must start fast and stay up; chaining them stalls every app restart behind a 5–9 min check and yields no clean pass/fail. Correct design = separate jobs, typecheck run **standalone** so it gets the whole box.

**How to apply:**
- Run `typecheck` **standalone** — stop `Start application` first (app ~4GB + check ~3.4GB OOMs). The merge-gate use case is naturally standalone.
- Do not foreground a full `tsc` in a bash tool call: it exceeds the 2-min tool cap. Run it as the workflow (unbounded) or as a detached `setsid` background process and poll a done-file.
- `tsc -p <cfg> --listFilesOnly | wc -l` is a fast way to prove a split config resolves the intended file set without a full (slow) type-check.
- Even faster future option: TS project references with `tsc --build` (incremental across projects) — not done; would need `composite`/`declaration` which conflicts with the current `noEmit`/`allowImportingTsExtensions` setup, so it's a larger change.
- **tsgo (`@typescript/native-preview`, TS7 native compiler) was empirically tested on THIS repo and is NOT viable as the gate yet.** It is installed and wired as an opt-in `check:fast` (`tsgo -p tsconfig.json --noEmit`), but its full strict check **does not complete** here: across 5 runs (concurrent AND standalone with ~5GB free) the process was silently killed (kernel OOM — zero output, no `.tsbuildinfo` written) after 150–200s+. The flattering "~16s / 2.1GB" first run was only parse+bind **aborting early on config errors**, NOT a real check — do not mistake that for success. Headline "10×/half-memory" benchmarks do not hold for this repo's type complexity on the preview compiler. So: tsc-split stays the default/reliable gate; re-test `npm run check:fast` periodically as TS7 matures. **Why:** chose tsc default over tsgo despite user preferring "tsgo fast default", because tsgo demonstrably can't finish here — honesty over headline speed.
- **tsgo config compat (needed for `check:fast` to even start) is also a forward-compat win for tsc:** TS7 **removed** `baseUrl` and `downlevelIteration` (error TS5102). Both were deleted from `tsconfig.json`. Verified safe for stable tsc: `paths` resolve relative to the tsconfig dir without `baseUrl` (TS4.1+); our `paths` values already start with `./`; no bare baseUrl-style imports exist (vite uses its own `resolve.alias`, tsx doesn't use tsconfig-paths). Confirmed with a single-file `@shared/*` import compiled under stable tsc — resolved fine (no "Cannot find module"). `downlevelIteration` is a no-op at our ES2020 target.
- Gotcha: `pkill -f 'tsc ...'` / `pgrep -f 'bin/tsc'` will match the killing shell's **own** command line and self-kill (exit 137). Split the pattern in a var (e.g. `PAT="bin""/tsc"`) or kill by PID file. Also note the IDE runs `tsserver.js` (language server) continuously — that is NOT a stray `tsc --noEmit` run.
- Detached background jobs (`setsid … & disown`) launched from a bash tool call are **reaped when that tool call returns** in this environment — they die silently with zero output, which looks identical to an OOM. Do NOT trust `setsid` for long checks; run them as a **platform-managed workflow** (survives across calls) and poll its logs. The earlier "tsgo silently killed" runs are at least partly this mechanism, not necessarily kernel OOM.

## The split gate COMPLETES, but the codebase is NOT typecheck-clean (huge latent backlog)
A full standalone production-parameter run (`NODE_ENV=production`, 4GB heap, app stopped) finally ran to completion — and that is the whole point: the OOM was always **hiding a massive pre-existing error backlog**, not protecting a clean build.
- **The server/shared half alone reports `Found 8104 errors in 467 files`.** The client half never even ran — `npm run check` chains the two halves with `&&`, so the server failure short-circuits before client (`0` `client/src` errors observed = client unmeasured, not clean).
- **This is NOT caused by the `baseUrl`/`downlevelIteration` removal:** only **8** of 8104 are `Cannot find module` (TS2307). The rest are genuine semantic errors — top codes: TS2339 (405, property doesn't exist — many are Drizzle schema/column mismatches, same family as the "Drizzle silently drops writes to non-existent columns" lesson), TS2769 (no overload matches), TS18046 (`unknown`), TS2322 (not assignable). Module resolution is sound.
- **Implication for "is this a merge gate?":** mechanically the runner is reliable (splits, completes, exits with a real pass/fail). But a strict zero-error gate **fails on a clean checkout today** — the baseline is deeply red. To use it as a gate you must either (a) burn down the 8104+ backlog (large, multi-task effort; note `hybridStorageService.ts` — a do-not-touch file — itself has 1 error, and `AI training server/` is off-limits), or (b) switch to a **baseline-diff gate** that fails only on NEW errors vs. a recorded baseline. Until then, treat `npm run check` as a **reporting/triage tool**, not a binary pass/fail.
- **Honesty note for future-me:** earlier in this work I called the gate "reliable, I'd ship it" having only ever validated **config correctness + file resolution** (`--listFilesOnly`), never a completed type-check — because it always OOM'd. Don't claim a gate "passes" until a full run has actually exited green at least once.
